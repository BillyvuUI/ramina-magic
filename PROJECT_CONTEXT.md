# PROJECT_CONTEXT.md

## Проект

**Название:** Ramina Magic  
**Репозиторий:** `BillyvuUI/ramina-magic`  
**Пользователь приложения:** Рамина  
**Назначение:** детское PWA-приложение для домашних заданий, накопления игровой валюты и магазина наград с обязательным подтверждением родителя.

## Основные требования продукта

- Имя ребёнка: **Рамина**.
- Валюта: **Крузейрики**.
- Визуальный стиль: девчачий, мягкий, розово-сиреневый, единороги, магическая тематика.
- Основные разделы:
  - Сегодня / задания.
  - Магазин.
  - История.
  - Родительский режим.
- Выполнение задания начисляет Крузейрики.
- Покупка в магазине **не должна списывать Крузейрики сразу**.
- Любая покупка сначала создаёт запрос со статусом `pending`.
- Списание происходит только после подтверждения родителем.
- Родительский PIN по умолчанию: **2580**.
- PIN должен быть сменяемым из родительского режима.

## Архитектурный принцип

Критически важно:

**НЕ использовать один большой JSON со всем состоянием приложения.**

Причина: в старом приложении для Самира такая архитектура приводила к тому, что одно устройство могло перезаписать свежие данные старым состоянием и откатывать матчи, задания, магазин и другие разделы.

В Ramina Magic данные изначально должны храниться раздельно.

### Текущая структура Firestore

Корень:

`apps/ramina`

Основные пути:

```text
apps/ramina/profile/main
apps/ramina/settings/main
apps/ramina/tasks/{taskId}
apps/ramina/completions/{YYYY-MM-DD_taskId}
apps/ramina/rewards/{rewardId}
apps/ramina/purchases/{purchaseId}
```

Допускаются дополнительные служебные документы/коллекции, если они не ломают этот принцип.

Изменения баланса должны выполняться безопасно.

Особенно:

- снятие Крузейриков при отмене выполнения;
- списание при подтверждённой покупке;
- любые операции, где параллельные действия с нескольких устройств могут конфликтовать.

## Магазин

Логика покупки:

1. Рамина нажимает `Хочу`.
2. Создаётся запись покупки со статусом `pending`.
3. Баланс пока НЕ меняется.
4. Родитель входит по PIN.
5. Родитель нажимает:
   - подтвердить;
   - отклонить.
6. При подтверждении:
   - транзакционно проверяется текущий баланс;
   - Крузейрики списываются;
   - purchase получает статус `approved`.
7. При отказе:
   - статус меняется на `rejected`;
   - баланс не меняется.

## Текущая проблема

### Медленный отклик интерфейса

Сейчас основная проблема:

**галочка задания и другие действия ощущаются медленнее, чем в приложении Самира.**

Отклик может занимать примерно 1–3 секунды.

Цель:

**интерфейс должен реагировать визуально мгновенно**, не дожидаясь ответа Firestore.

Желаемое поведение:

```text
нажатие
→ UI меняется сразу
→ Firebase сохраняет в фоне
→ при успехе ничего визуально не меняется
→ при реальной ошибке UI откатывается и показывается сообщение
```

## Почему текущий optimistic UI всё ещё может тормозить

Была сделана попытка optimistic UI, но остаётся возможная гонка:

1. пользователь нажимает галочку;
2. локальное состояние меняется;
3. вызывается `render()`;
4. Firestore `onSnapshot` может почти сразу прислать ещё старое серверное состояние;
5. listener перезаписывает optimistic state;
6. после завершения transaction приходит новое состояние;
7. галочка окончательно появляется.

Из-за этого пользователь всё равно может ощущать задержку.

### Что нужно исправить

Во время незавершённой операции по конкретному заданию:

- `onSnapshot` НЕ должен отменять optimistic состояние этого задания;
- `onSnapshot` НЕ должен визуально откатывать optimistic изменение баланса;
- после завершения transaction локальное состояние должно синхронизироваться с подтверждённым серверным состоянием;
- при ошибке optimistic state корректно откатывается.

Возможные подходы:

- overlay/map pending operations поверх server state;
- отдельный optimistic layer;
- игнорирование конфликтующих snapshot-обновлений до завершения конкретной pending operation;
- точечное DOM-обновление вместо полного `render()` на каждое событие, если это упростит UX.

Важно сохранить безопасность транзакций.

## Offline cache

**Постоянный Firestore offline cache специально не включать без отдельного обсуждения.**

Причина: в старом приложении Самира persistent cache и старые клиенты способствовали откатам состояния.

Для этого проекта важнее:

- предсказуемость;
- сервер как подтверждённый источник;
- корректная multi-device синхронизация.

---

## Безопасность

Текущая безопасность достаточна только для домашнего тестирования.

Сейчас:

- Anonymous Auth включён;
- Firestore Rules требуют `request.auth != null`.

Но в будущем нужно улучшить:

1. **Firebase App Check**.
2. Ограничение Firebase API key при необходимости.
3. Более строгую авторизацию родителей/ребёнка.
4. Разделение прав:
   - ребёнок может выполнять задания и создавать запрос покупки;
   - родитель может редактировать задания, награды, PIN и подтверждать покупки.
5. Никогда не хранить настоящие server-side secrets в публичном GitHub.

Firebase Web API key сам по себе не является секретом, но service account keys, Admin SDK private keys и другие приватные credentials в репозиторий класть нельзя.

## Исторический контекст

Проект Ramina Magic создаётся после опыта с приложением для Самира `road-to-dream`.

В старом приложении главная проблема была в синхронизации:

- почти всё состояние хранилось одним большим JSON;
- старый клиент мог загрузить старый cache;
- затем записать старый JSON обратно;
- это удаляло более свежие изменения с других устройств.

Для Самира проблему пришлось решать отдельным V3-документом и отказом от persistent cache.

**В Ramina Magic нельзя повторять эту архитектурную ошибку.**
